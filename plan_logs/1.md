# 共享雷达 FDCAN 发送方案

## Summary

采用一个统一的 FDCAN 发送出口，避免雷达和二维码同时抢 `/dev/ttyACM0`。  
雷达继续发 16 字节 CAN FD 坐标包，二维码继续发 8 字节普通 CAN 包，二者共用同一条 FDCAN 总线，但主机侧只允许一个进程直接打开 FDCAN 设备。

## Key Changes

- 新增/改造一个轻量 `fdcan_gateway`：
  - 独占打开 Openlight CANable2 `/dev/serial/by-id/usb-Openlight_Labs_CANable2...`
  - 支持发送 classic CAN 8 字节帧和 CAN FD 16 字节帧
  - 雷达坐标仍按 `0x12 + <x,y,z,yaw>` 四个 float32 little-endian 发出
  - 二维码仍按 `0x501/0x502 + 8 bytes` 发出，不改二维码协议

- 雷达侧改为“提交发送请求”：
  - `canfd_pose_sender` 不再直接打开 `/dev/ttyACM0`
  - 保留 `/robot/pose_continuous -> CAN ID 0x12 -> 16 bytes -> 100Hz`
  - stale timeout、重启指令监听、debug CSV 保持现有逻辑

- 二维码侧改为“提交发送请求”：
  - 停用 `rc-canable.service`，禁止它用 `slcand -s8 /dev/ttyACM0 can0`
  - 二维码不再初始化 `can0`，不再抢 `/dev/ttyACM0`
  - 二维码发送 `0x501/0x502` 仍保持 8 字节

- 开机自启顺序：
  - 先启动 `fdcan_gateway`
  - 再启动雷达栈和二维码程序
  - 如果 FDCAN 掉线，只有 gateway 负责重连，避免多个程序重复激活设备

## Why This Solves It

- CAN FD 总线支持普通 8 字节 CAN 帧和 16 字节 CAN FD 帧共存。
- 雷达和二维码的 CAN ID 不冲突：雷达 `0x12`，二维码 `0x501/0x502`。
- `0x12` 仲裁优先级高于 `0x501/0x502`，二维码不会抢雷达坐标发送优先级。
- 避免两个进程同时打开 `/dev/ttyACM0`，这是当前失败的根因。

## Test Plan

- 启动前确认没有旧服务占用：
  - `rc-canable.service` 已停止并禁用
  - 没有 `slcand ... /dev/ttyACM0 can0`
- 启动后确认：
  - gateway 成功打开 Openlight CANable2
  - 雷达 100Hz 坐标包仍在发，payload 为 16 字节
  - 二维码触发时发出 `0x501/0x502` 8 字节帧
  - 拔插 FDCAN 后 gateway 自动重连，雷达和二维码不重复激活设备
- 运行验证：
  - 电控能收到雷达坐标
  - 电控能收到二维码指令
  - 雷达重启指令仍有效

## Assumptions

- 二维码接收端希望继续收到普通 8 字节 CAN 帧，而不是 CAN FD 帧。
- 雷达坐标包必须保持 16 字节 CAN FD，不拆包、不降级成 8 字节。
- 当前 Openlight CANable2 继续使用现有 slcan_fd 协议，不强依赖刷固件或改成原生 SocketCAN FD。
- 这版优先保证鲁棒和少改主链路，不追求最漂亮的纯 SocketCAN 架构。
